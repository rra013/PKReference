Part 1. The system in ten minutes

What it is

The PK Reference backend is a small data pipeline and read-only API for a Pokémon reference app. It does three things:

  1. Collects. It polls two public sources: Limitless, for tournament events (who played, their teams, who beat whom), and Smogon, for monthly statistics of the Pokémon Showdown ladder.
  2. Keeps. Everything fetched goes through Kafka topics that are never emptied, and from there into PostgreSQL tables. The topics are the record of what was fetched; the tables are a view of it that can be rebuilt by reading the topics again.
  3. Answers. A JSON API at /v1 serves insights worked out from the tables: how often each Pokémon is used, how it does in top cuts, win rates from match results, trends, common sets, cores and archetypes, and the ladder's numbers.

Why it exists. Before it, every copy of the app crawled Limitless by itself, which is slow, repeats the same work on every device and runs into Limitless's rate limit (50 requests in 5 minutes). One server crawling once for everyone is lighter on the source, and it can keep match results, which lets it compute things a device can't, such as win rates that leave out mirror matches.

The one idea to hold on to

The system is split at Kafka into a write path and a read path.

  • The write path runs on timers and on Kafka records, never on a user's request: discover what to fetch, fetch it, publish it, store it. It is slow on purpose (rate limits) and built to be repeated safely.
  • The read path runs on HTTP requests: a filter checks the caller, a controller calls a service, the service reads the tables and computes the answer, and the answer is cached. It never calls Limitless, Smogon or Kafka.

The two paths share only the database. If the sources or Kafka are down, the API keeps answering from what is stored.
