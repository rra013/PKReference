Part 2. Follow the data

Three walks through the code. Each step names the class and method that does it; Part 8 has every one of them in detail.

2.1 The life of a tournament event

  1. The timer fires. Every 30 minutes Spring's scheduler calls EventDiscovery.poll() (@Scheduled). For each configured format it calls discover(format).
  2. List. discover asks LimitlessClient.tournaments(format, page) for the newest events, a page of 50 at a time, walking back until a whole page is older than the lookback (7 days). Every request first waits its turn in RequestThrottle.acquire().
  3. Decide. For each listed event, FetchPolicy.shouldRequest(...) answers "ask for it now?" from the event itself and from what the event_fetch table remembers (EventFetchRepository.find): at least 16 players, already started, not already final, not already waiting in the queue, and if fetched before, not within the last 6 hours.
  4. Ask. For each "yes", discovery publishes a TournamentDiscovered record to the topic tournaments.discovered, keyed by the event's id, waits for the broker to confirm (KafkaSends.await), and notes it in event_fetch (markRequested).
  5. Fetch. EventFetcher.onDiscovered(...) (@KafkaListener, group standings-fetcher) receives the record and makes three throttled requests: the event's details, standings and pairings. It works out whether the standings are final (FetchPolicy.isFinal: fetched 48 hours or more after the start).
  6. Publish. The fetcher sends a StandingsFetched record to standings.fetched and a PairingsFetched record to pairings.fetched, both keyed by the event's id, waits for both, then calls markFetched. Only then does the method return and the offset move on.
  7. Store. Two independent consumer groups read standings.fetched:
    • TeamStoreConsumer.onStandings (group team-store-standings) calls TeamStore.putStandings, which in one transaction deletes the event's old rows and inserts its event, phases, teams, members and moves. Each member gets its species key from SpeciesVocabularies.identify. The store's version counter goes up by one.
    • UsageConsumer.onStandings (group usage-aggregator) calls UsageAggregationService.apply, which adds the event to the all-time counters once it is final, and marks it processed in the same transaction.
    TeamStoreConsumer.onPairings (group team-store-pairings) stores the matches through TeamStore.putPairings.
  8. Serve. The next request to /v1/formats/M-C/pokemon finds a new store version, so MetaService recomputes from the tables, and the new event is in the numbers.
  9. Again, until final. An event fetched before its standings settled is asked for again every 6 hours (step 3) until a fetch comes 48 hours after its start. Each later fetch replaces the earlier rows.

2.2 The life of a ladder month

  1. The timer fires. Every 12 hours LadderDiscovery.poll() calls discover().
  2. List. SmogonClient.months() reads Smogon's index page; for each of the two newest months, chaosFiles(month) reads that month's listing. The client waits 2 seconds between requests.
  3. Choose. Each file name is split into a format and a rating. LadderFormat.parse recognizes Champions doubles and singles formats of a known regulation; everything else is skipped. LadderStore.has(...) skips files already stored by the current rule.
  4. Fetch and reduce. For each file left, discovery gets the small leads table (SmogonClient.leads) and then streams the big statistics file (SmogonClient.chaos) straight into LadderReducer.reduce, which reads one Pokémon at a time and keeps only what the app shows. Up to 7 MB becomes about 1 MB.
  5. Publish. The reduced Ladder.Stats, wrapped in StatsFetched with the time, goes to the topic ladder.stats, keyed format|month|rating.
  6. Store. LadderStoreConsumer.onStats (group ladder-store) calls LadderStore.put, which keeps the record as JSON text in ladder_stats unless a newer one is already there.
  7. Serve. GET /v1/ladder/{format} reaches LadderService.stats, which reads the row and adds each Pokémon's change since the previous month and its usage at the other ratings.

A published month never changes, so each file is fetched exactly once. After the first run a poll is three small listing requests and nothing else, until a new month appears.

2.3 The life of an API request

Take GET /v1/formats/M-C/pokemon?window=30d with an access token.

  1. Tomcat accepts the connection and runs the servlet filters in order.
  2. ApiAuthFilter runs first. With keys configured it reads the Authorization: Bearer ... header and has TokenService.verify check the token's algorithm, signature, expiry and claims. A bad or missing credential ends here with a 401. With no keys configured the filter lets everything through.
  3. The ETag filter (registered in MetaWebConfig for /v1/*) wraps the response so it can hash the body later.
  4. Spring MVC matches the path to MetaController.pokemon(format, window), converting {format} and ?window= into its arguments.
  5. The controller turns "30d" into a MetaWindow (anything else is a 400) and calls MetaService.pokemon.
  6. The service builds a cache key from the request, the store's version and the hour. On a hit it returns the remembered answer. On a miss it reads rows through MetaRepository, counts in memory, and remembers the result.
  7. Jackson writes the returned record as JSON. The controller added Cache-Control: max-age=900.
  8. On the way out the ETag filter hashes the body: if the request's If-None-Match has the same hash, the client gets 304 Not Modified and no body. The auth filter's wrapper has turned public into private in the caching header. Tomcat gzips bodies over 2 KB.

2.4 When things go wrong

What happensWhat the system does
Limitless is down or answers an error while an event is being fetched EventFetcher.onDiscovered throws. The error handler retries the record 3 times, 2 seconds apart, then parks it on tournaments.discovered.DLT. Nothing was marked fetched, so after 24 hours discovery treats the request as lost and asks again.
Limitless answers 429 (too many requests) LimitlessClient.withRetry waits for the time its Retry-After header gives (at most 30 seconds) and tries again, up to 3 attempts. The throttle also reads Limitless's own count of what is left and stops sending before the limit.
The broker is down when discovery publishes KafkaSends.await throws after 30 seconds. Discovery logs it and does not mark the event requested, so the next poll asks again.
The server stops between publishing standings and committing the offset On restart the fetcher gets the same record again and fetches the event again. The stores replace the event's rows, and the counters skip an event already marked processed, so the repeat changes nothing.
A record can't be stored (a bug, a constraint) The transaction rolls back, the record is retried, then goes to its DLT. Other records carry on.
Kafka and both sources are down The API keeps answering from Postgres. Nothing new arrives until they are back.
Postgres is down Requests fail with a 500. A listener fails, retries 3 times over 6 seconds, and the record goes to its DLT. Nothing is lost, because standings.fetched, pairings.fetched and ladder.stats keep every record: once the database is back, resetting the stores' consumer groups reads them in again. (A longer back-off would ride out a short outage by itself; see Part 11.)
The tables are lost or a counting rule changes Reset the consumer groups' offsets to the start and the tables are rebuilt from the topics (README, "Rebuilding the counters and the store").
