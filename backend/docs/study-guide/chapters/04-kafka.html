Part 4. Kafka, as this project uses it

4.1 The ideas

Topic
A named, append-only log of records. Producers add to the end; consumers read forward from wherever they are. Reading does not remove anything.
Record
A key, a value and some headers. Here the key is always a string (an event id, or format|month|rating) and the value is JSON.
Partition
A topic is split into partitions, each an ordered log. A record's key decides its partition (by hash), so records with the same key stay in order. Each topic here has 3.
Offset
A record's position in its partition. A consumer's progress is "the next offset to read".
Consumer group
A name under which consumers share progress. Kafka stores each group's offsets. Two groups reading one topic each see every record, independently; two consumers in one group split the partitions between them.
Compaction
A cleanup policy that, instead of deleting old records by age, keeps at least the newest record of each key. A compacted topic behaves like a table of "latest value by key" that can still be read from the beginning.
Dead letter topic (DLT)
A topic where records are parked after repeated failure, so they can be inspected and the rest of the topic isn't blocked.
KRaft
Kafka running its own metadata quorum, with no ZooKeeper. This project runs one node that is both broker and controller.

4.3 Why Kafka at all

Not for volume: a few hundred events a month would fit in a queue table. Kafka is here as a durable, replayable log:

  • Replay. The compacted topics hold every event ever fetched. If a table is lost, or a rule changes (how names are standardized, what counts as a species), the tables are rebuilt by resetting a consumer group to the beginning. Limitless doesn't have to be crawled again.
  • Independent readers. The team store and the usage counters both read standings.fetched without knowing about each other. Adding a third reader is a new group id.
  • Decoupling slow from fast. Discovery takes seconds; fetching is throttled and can take hours during a backfill. The queue between them survives restarts.
  • Failure isolation. A record that can't be processed is retried and then set aside, without stopping the others.

The honest cost: a broker is more to run than this volume needs. The plan calls that out, and keeps it to a single KRaft node.

4.4 Delivery guarantees

Producer. acks=all and enable.idempotence=true: a send succeeds only when the broker has the record, and a retried send isn't stored twice. Every send is awaited, so "published" means confirmed.

Consumer. Spring Kafka commits offsets only after the listener has returned for the records it was given. If the process dies before the commit, those records are delivered again. That is at-least-once delivery: never lost, sometimes repeated.

So every consumer is idempotent: handling a record twice ends in the same state as handling it once.

  • TeamStore deletes an event's rows and inserts them again, in one transaction, and ignores a fetch older than the one stored (by fetchedAt).
  • LadderStore replaces a row unless the stored one is newer.
  • UsageAggregationService can't "replace" a counter, so it records each processed event's id in the same transaction as the counts and skips an id it has seen.
  • EventFetcher repeating a fetch costs three requests and republishes; compaction and the stores absorb the duplicate.

At-least-once delivery plus idempotent handling gives the effect people mean by "exactly once", without Kafka transactions.

4.6 Errors: retry, then dead-letter

KafkaErrorHandling defines one DefaultErrorHandler: when a listener throws, retry the record up to 3 more times, 2 seconds apart; if it still fails, publish it to <topic>.DLT on the same partition and continue with the next record.
