5.2 Flyway

The schema lives in src/main/resources/db/migration as V1__...sql to V5__...sql. At start-up Flyway runs any file that hasn't run on this database, in number order, and records each in its own table, flyway_schema_history, with a checksum.

  • To change the schema, add a new file with the next number. Never edit one that has been applied: Flyway compares checksums at start-up and refuses to start on a mismatch. (This is why the comment pass that produced this guide left the SQL files alone.)
  • Hibernate is set to ddl-auto: validate: it creates nothing, and only checks that the two entity classes match their tables.
  • Tests run the same migrations on H2 (in memory) and, where Docker is available, on real Postgres 17 through Testcontainers, because H2 accepts some SQL that Postgres rejects.

5.3 Two styles of data access, and why

The first version of the backend used JPA: annotate a class as an @Entity, declare a repository interface, and let Spring Data generate the queries. It's concise for "load a few objects, change them, save them", which is what the counters do.

Everything since uses JdbcTemplate and plain SQL. The team store's work is "delete an event's rows and bulk-insert a few thousand", and the insights' work is reporting queries over joins. Both read more plainly as SQL, batch well, and behave the same on H2 and Postgres. The counting itself is done in Java, not SQL, so definitions live in one tested place (MetaService).

5.4 Transactions and the version counter

TeamStore.putStandings is @Transactional: delete, bump store_version, insert, all or nothing. A reader on another connection sees either the old event or the new one, never half.

MetaService caches each computed answer under a key that includes store_version. Because the bump commits in the same transaction as the rows, a reader sees a new version exactly when it can see the new rows, so a cached answer is never served for data it wasn't computed from.
