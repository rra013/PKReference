Part 6. Signing in

The server is meant for one owner's devices, reached over a private network (Tailscale). By default it listens on 127.0.0.1 only and lets every request in. When API keys are configured, every request must be signed in. The whole mechanism is five classes in security/; Spring Security isn't used.

6.1 Two credentials

What it ispkr_ plus 32 random bytes, base64url. Made by scripts/new-api-key.sh.A JWT signed with HMAC-SHA256.
LivesUntil its hash is removed from the server's settings15 minutes

What the server storesOnly its SHA-256 hash (PKREF_API_KEY_HASHES) Nothing: it verifies the signature

Why two. The long-lived secret travels once every 15 minutes instead of with every request, and a token that leaks stops working by itself. Storing only the key's hash means the server's configuration, backups and logs never contain a usable key.

6.2 The flow

  1. The app sends POST /v1/auth/token with Authorization: Bearer <key>.
  2. ApiAuthFilter hashes the key and compares it with every configured hash, each in constant time (MessageDigest.isEqual). On a match it stores the key's short id (the first 8 hex digits of its hash) on the request and lets it through.
  3. AuthController.token asks TokenService.issue(keyId) for a token and returns it with Cache-Control: no-store.
  4. For every other request the app sends Authorization: Bearer <token>, and the filter calls TokenService.verify.
  5. When a token is refused with token_expired or invalid_token, the app trades its key again and repeats the request once.

6.3 What a token contains

Three base64url parts joined by dots: header, claims, signature. The first two are readable by anyone; the signature is what makes them trustworthy.

6.4 The order of checks in TokenService.verify, and why

  1. Parse. Not three dot-separated parts: MALFORMED.
  2. Algorithm. The header is written by whoever sent the token, so the server decides the algorithm. This closes the classic JWT attacks: alg: none (no signature) and algorithm switching.
  3. Signature. HMAC-SHA256 with the server's secret. Only after this are the claims the server's own words.
  4. Expiry.
  5. Issuer, audience, subject. A token signed by this server for something else is not accepted.
  6. Key still configured. Removing a key's hash from the settings ends its tokens too.

6.5 Details an interviewer may probe

  • The signing secret is 32 random bytes generated at start-up unless PKREF_TOKEN_SECRET is set. A restart therefore ends all tokens; clients just trade their key again.
  • Credentials are never read from the URL (where proxies and logs keep them) and never logged. The refusal log line names the path and the reason only.
  • Swagger UI's paths are open, but a path that the server would rewrite (containing .., %, ; or //) never counts as documentation.
  • A token can't be traded for a token. The token path only accepts a key, and AuthController checks again that the filter matched one.
  • Caching. Signed-in answers have Cache-Control: public rewritten to private, so a shared cache can't serve them to someone else.
  • What this is not. No users, roles or sessions; no refresh tokens (the key plays that part); no token revocation list (a 15-minute life and key removal stand in for it). A public deployment would need more, as the plan says.
