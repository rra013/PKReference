Part 11. Design decisions, and questions to expect

Short answers you can say aloud, each with the code that backs it up. Where the honest answer is "it's a limitation", that's what is written: an interviewer hears a trade-off understood, which is better than a defence.

Architecture

Why Kafka for a few hundred events a month?

For replay, not throughput. The fetched data stays in compacted topics for good, so any table can be rebuilt, with new rules, without crawling Limitless again. It also gives independent consumers and isolates the slow, rate-limited fetching from everything else. The cost is running a broker, kept to one KRaft node. A queue table in Postgres would handle the volume; it wouldn't give replay as naturally. (Part 4.3)

Why are the insights computed on request instead of stored in tables?

At a few thousand teams a format, counting in memory takes milliseconds, and the result is cached until the data changes. Storing aggregates would mean migrations and backfills every time a definition changed. If a format grew to where this was slow, the plan is to move that insight to its own consumer with its own tables, rebuilt from the topics. (MetaService)

How do you know a cached answer isn't stale?

The cache key includes store_version, a counter that TeamStore increments inside the same transaction as every write. A reader sees the new version exactly when it can see the new rows. The key also includes the hour, because windows like "the last 14 days" move even when nothing is written. (MetaService.memoize)

What are the write path and read path, and why separate them?

Writes are driven by timers and Kafka records; reads by HTTP requests. They share only Postgres. So an outage of Limitless, Smogon or Kafka costs freshness, not availability, and a slow backfill never slows a request.

Why split discovery from fetching?

Discovery is one cheap list call per page; fetching is three throttled calls per event and can run for hours. With a topic between them, a poll finishes quickly, a failed fetch retries alone, and pending work survives a restart. (EventDiscovery, EventFetcher)

Kafka

What delivery guarantee do you have?

At-least-once consumption, with idempotent handlers, which gives exactly-once results. Producers use acks=all with idempotence and every send is awaited. I don't use Kafka transactions: the handlers write to Postgres, so the idempotence has to live there anyway. (Part 4.4)

How is each consumer idempotent?

The team store deletes and re-inserts an event in one transaction and ignores a fetch older than the stored one. The ladder store replaces a row unless the stored one is newer. The counters, which can't be "replaced", record each processed event id in the same transaction as the counts.

What happens to a record that keeps failing?

Three retries two seconds apart, then it's published to <topic>.DLT with the exception in its headers, and the consumer moves on. (KafkaErrorHandling)

What is compaction and why use it here?

The broker keeps at least the latest record per key instead of deleting by age. Keyed by event id, the topic holds the latest standings of every event ever fetched: a durable table I can re-read. An event fetched five times before its standings settled takes the space of one.

Why max-poll-records: 10 and a 15-minute max.poll.interval.ms?

The fetcher makes three requests per record under a 40-per-5-minutes throttle, so one batch can take many minutes. If a consumer doesn't poll within the interval, Kafka assumes it died and reassigns its records, which would fetch events twice and spend the rate limit. Small batches and a long interval prevent that.

Why three partitions with one consumer each?

Three leaves room to run more consumers in a group later without repartitioning. Today each listener is one thread reading all three. Records with the same key share a partition, so an event's updates stay in order.

Why JSON and not Avro or Protobuf with a schema registry?

Simplicity at this size: the records are Java records, readable in Kafka UI, and tolerant of added fields (ignoreUnknown). The trade-off is no enforced schema evolution. With more producers or teams I would add a registry.

Spring and Java

What does @Bean do, and when do you use it instead of @Component?

@Bean goes on a method of a @Configuration class; Spring calls it once and registers the result. I use it when the object needs construction logic or isn't my class: the Clock, the NewTopics, the error handler, the filter registrations, the TokenService. @Component and its relatives go on my own classes that Spring can construct directly. (Part 3.2)

Why constructor injection?

Dependencies are explicit and final, the class can't exist half-wired, and tests construct it with fakes without starting Spring.

Why inject a Clock?

So time is an input. Tests check "is this event final 48 hours after it started?" or "does this token expire at 15 minutes?" at exact instants.

How does @Transactional work, and what's the catch?

Spring wraps the bean in a proxy that opens a transaction before the method and commits or rolls back after. The catch: it only applies to calls that come through the proxy, so a method calling another @Transactional method on this gets no new transaction. Here each transactional method is called from another bean.

Why JdbcTemplate in most places and JPA in one?

JPA came with the first version and suits its small load-modify-save counters. The rest is bulk replaces and reporting joins, which are clearer and faster as SQL. (Part 5.3)

Why records?

Wire types, responses, settings and query rows are all plain immutable data. A record is that in one line, and Jackson maps it to JSON by field name.

The sources

How do you stay under Limitless's rate limit?

RequestThrottle keeps a sliding window of the requests sent (40 in 5 minutes, under the 50 allowed) and also reads Limitless's own ratelimit header, because the app on the same machine shares the address. Every request passes through it via a RestClient interceptor. On a 429 the client honors Retry-After.

How do you decide when an event's standings are final?

By the app's rule: a fetch made 48 hours or more after the event started is final. Until then the event is stored, so it can be seen, and fetched again every 6 hours. The all-time counters wait for the final fetch. (FetchPolicy)

Player-typed names are messy. How do you count them?

NameStandardizer maps each item, ability and move to a canonical spelling using the game's own lists: exact match after normalizing, then a single near miss by edit distance, otherwise kept as typed. Species use the app's own vocabulary (SpeciesVocabulary), and a golden file checked by both test suites keeps server and app in agreement.

Why reduce Smogon's files instead of storing them?

A file is up to 7 MB, over the topic's limit and far more than the app shows. The reducer streams it one Pokémon at a time and keeps about 1 MB. Smogon keeps every month, so the raw file can always be fetched again; a version number on the rule makes the server do that when the rule changes. (LadderReducer)

Security

Why trade a key for a JWT instead of sending the key every time?

The long-lived secret is exposed once every 15 minutes rather than on every request, and a leaked token expires by itself. The server stores only the key's SHA-256 hash.

What JWT attacks does verify guard against?

It pins the algorithm to HS256 before checking the signature (no alg: none, no algorithm switching), checks expiry, issuer and audience, and checks that the key the token was issued for is still configured. (Part 6.4)

Why constant-time comparison?

A normal comparison returns at the first differing byte, so response time leaks how much of a guess was right. MessageDigest.isEqual takes the same time regardless, and every configured hash is compared.

Why not Spring Security?

The need is one check on every request and one token endpoint. A servlet filter and a small service do that in a few hundred lines that can be read end to end. With users, roles or OAuth I would switch.

Limits, and what I would change

What are this system's weak points?

  • One of everything. One broker with replication factor 1, one Postgres, one server instance. A disk loss is recovered from the daily backup and by fetching again, not by failover.
  • Scheduling assumes one instance. Two instances would both poll. The event_fetch table and idempotent stores make that wasteful rather than wrong, but a lock (ShedLock, or a leader) would be the fix. The throttle and the cache are also per instance.
  • Short retries. Six seconds of retrying doesn't outlast a database restart; those records go to the DLT and need a replay. A longer exponential back-off, or pausing the listener, would be better.
  • Nobody watches the DLTs. There's no alert on dead letters or on ingest lag yet; it's in the plan's launch phase.
  • The cache is crude. A map cleared when it passes 500 entries. Fine for one user; a real cache with size and time limits (Caffeine) is the obvious upgrade.
  • ETags save bytes, not work. The filter hashes a body the server has already produced.
  • Test isolation. The database slice tests commit rather than roll back, so some tests clear their tables first. Found while writing the ladder tests; noted for a fix.

How would this scale to many users?

Reads scale first and easily: the API is stateless apart from its cache, so more instances behind a load balancer and a CDN in front (the answers are identical for everyone and already carry caching headers). Writes barely grow with users, since the sources are the same. For more sources or volume: more partitions and consumers per group, a replicated Kafka cluster, and precomputed projections for the heaviest insights.

What would you build next?

Monitoring (lag, newest event's age, dead letters), a webhook from Limitless in place of polling, and a replay test that rebuilds a table from its topic and checks it is identical.
